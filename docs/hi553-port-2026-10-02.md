## What the driver is

V4L2 subdev (CCI/regmap, subdev state, runtime PM, enable_streams — same
house shape as imx351). Three modes: 2560x1920, 2560x1440, 1280x720, all
2816x2083 line/frame at 30 fps, 2-lane RAW10 at a 440 MHz link. Controls:
exposure, analogue gain, vblank (+ pixel rate / link freq / hblank RO).

## Register-data provenance (from hi553.c header/comments; verified where noted)

| Table | Source | Confidence |
|---|---|---|
| `hi553_init_ram_a/b/c` (8-bit writes, 0x2000–0x2bff) | libmmcamera_hi553.so, US998 30b, "byte-identical in LineageOS SGCMarkus vendor trees" per predecessor's header; SRAM-load order = LG mm-camera order | High (predecessor's extraction claim; sequential CCI_REG8 encoding matches the "8-bit load" description) |
| `hi553_init_pll` (0x0a00/0x0b0x/0x0c0x) + `hi553_init_mipi` | same library tables | High |
| mode tables 2560x1920 / 2560x1440 / 1280x720 | same library, per-mode output regs (smaller modes carry only deltas) | High |
| chip ID 0x0553 @ 0x0f16, streaming 0x0a00, 16-bit data | HI556/HI846 family map | Medium — bench-check |
| exposure reg 0x0126, gain reg 0x0077, gain range 0–240 | family layout, explicitly flagged in the source | Low-medium — bench-check first (AGC) |

Independent consistency checks I ran (all pass): mode table programs
0x0a12=0x0a00 (2560 wide), 0x0a14=0x0780 (1920 high), 0x0008=0x0b00
(2816 line length), 0x0006=0x0823 (2083 frame length); pixel_rate
2816x2083x30 = 175,971,840 matches the mode struct; 440 MHz x 2 lanes /
10 bits = 176 MP/s matches. SRAM tables run 0x2000..0x23fb / 0x23fc.. /
... contiguous with no gaps. Bayer order SGRBG10_1X10 is family-consistent
(hi556 uses the same) but unverified against the module — bench item.

## Board wiring provenance (downstream msm8998-joan tree, joan-camera_rev_0.dtsi)

- Bus: LG "i2c_8" = BLSP2 I2C2 = `blsp2_i2c2` (0xc1b6000), sensor 0x28,
  BRCF016GWZ EEPROM beside it. (SoC dtsi already provides blsp2_i2c2
  default/sleep pinctrl on GPIOs 6/7, matching downstream i2c_8 states.)
- MCLK2 = GPIO 15 `cam_mclk` (added `cam1_mclk_default` board state).
- VT_RESET = **TLMM GPIO 9**; VT_VDIG = **PM8998 GPIO 9** (module LDO enable,
  voltage never set downstream) → modelled as `cam1_dvdd_1p05` regulator-fixed
  at the sensor-nominal 1.05 V, mirroring the v1 CAM0_VDIG pattern.
- Rails: dovdd = `vreg_l14a_1p88` (downstream cam_vio = pm8998_l14), avdd =
  `vreg_l22a_2p85` (cam_vana = pm8998_l22). csiphy-sd-index = 2, csid 2.
- rotation <90> (LG qcom,mount-angle = <270>, Android-clockwise → mainline
  mirrored; same conversion as v1's imx351). orientation <0> (front).

Two corrections vs. the task brief (both resolved by downstream evidence,
documented in the commit and the dts comment):
1. brief said "pm8998_l6 1.8 V" — downstream front-cam I/O rail is
   **pm8998_l14** (both eeprom1 and qcom,camera@1 nodes); rear cam uses
   lvs1, matching v1's imx351 work. Lucy's hi553 node (l18, MCLK1) is a
   different board and was NOT used.
2. brief said "VT_RESET pm8998 gpio 9" — downstream gpio table: VT_RESET =
   **tlmm 9**, pm8998 gpio 9 is VT_VDIG (both lucy and joan agree).

## Integration dependency (read before bench)

This branch is based on latest-clean-test-synced, which predates the whole
MSM8998 CAMSS stack. So on this base: **no &camss SoC node, no camss
driver** — the CSIPHY2 port link is deliberately NOT in the dts (a bare
remote-endpoint phandle would not resolve). The sensor node therefore has
no `port`; until CAMSS merges, probe ends with "no endpoint" (-ENXIO).

The CAMSS work exists on `joan/hi553-front-camera` (v1) /
`joan/latest-clean-test-merged`: camss driver series (9cf96bb6e12e + fixes),
SoC dtsi (7b8b42e61e64, cdf958d56369, d3924b5f5221, d464a5fe2f6d), board
camss enable + imx351 node. When that lands, append to the hi553 node
(snippet also in the dts comment):

    port {
        hi553_ep: endpoint {
            data-lanes = <1 2>;
            link-frequencies = /bits/ 64 <440000000>;
            remote-endpoint = <&csiphy2_ep>;
        };
    };

plus `&camss { ports { port@2 { reg=<2>; csiphy2_ep: endpoint {
data-lanes = <0 1>; remote-endpoint = <&hi553_ep>; }; }; }; }` and the
camss vdda-supply (L2 1.2 V) / vdd_sec (L1) rails from v1's enable commit.

## Bench follow-ups

1. Probe: expect chip-id read at 0x0f16 → 0x0553; if ENODEV, the family
   chip-id guess is wrong — read 0x0000/0x0f16 raw on the bench.
2. First things to verify (flagged in source): exposure 0x0126, gain
   0x0077 + range 240 (AGC sanity), Bayer order GRBG vs BGGR.
3. Stream 2560x1920 @30 fps, verify 440 Mbps timing and no CCS hang on
   stop (driver powers off on stream stop like imx351, no autosuspend).
4. VDIG rail: confirm 1.05 V is right for this module (downstream never
   sets it); measure at PM8998 GPIO 9 LDO.
5. EEPROM coexistence on the bus (address 0x50-ish) — driver does not
   touch it; check no probe interference.
6. After CAMSS merge: add port link, then media-ctl pipeline test
   (CSIPHY2 → CSID2 → VFE) on US998 bench.
